# 010_oc-ledger 工作区部署

## 何时使用

- 用户要求部署、搭建或重建收口目录时使用本 skill，收口目录的根目录名固定为 010_oc-ledger。

- 新 agent 第一次接入一台已有收口目录的机器时也使用本 skill，走核对与补齐路径，不重建。

- 本 skill 只覆盖首次落地，顺序是创建骨架、收编、接入。换机迁移另有单独方案，不在本 skill 范围内，遇到时停下来问人。

- 执行中遇到本 skill 没写的情况时停下来问人，不自行发明，不拿其他文档的说法代替本 skill。

## 三性契约

### 可复用性

- 把所有随机器变化的值收进参数，在部署前确认阶段一次问清，任何步骤不得写死路径、机器名、身份或工具名。

- 本 skill 不引用任何其他文档，结构、命令、模板、规则、验收全部在本文件与 references 目录内，新 agent 只读本 skill 就能执行。

- 部署只依赖 mkdir、git 与 shell，不依赖任何产品专属工具，同一套步骤适用于任何一台机器。

- 写完本 skill 后检查全文，除占位符形式外不得出现绝对路径、真实人名、真实邮箱或任何秘密值。

### 幂等

- 每个阶段都以状态检查开头，目标状态已成立时只验证并跳过，不做任何改动。在已部署好的收口目录上重跑整个 skill 应产生零改动且验收全绿。

- 建目录使用 mkdir 加 p 参数，重复执行无副作用。

- 写根文件时只在文件不存在时创建，已存在的文件只核对与补齐，不覆盖。账本文件是唯一的覆盖写例外，且只按它自己的格式覆盖更新。

- 建仓库时只在没有 git 目录时初始化，只在本地身份未设置时写入身份，只在工作区有改动时提交。产物索引只在未跟踪时强制加入一次。

- 收编时先查该工具的抽取目录是否已存在，已存在则验证后跳过，不重复抽取，不产生重复副本。

- 试写入遵循创建、验证、删除三步，重复执行安全。

- 验收一节同时是幂等证明，重跑后验收全绿且 git status 干净即证明幂等成立。

### 扩展性

- 核心形状固定，阶段划分与验收标准不变，扩展只通过追加数据完成，不改核心步骤。

- 扩展点全部是追加式，新增接入约定只加一个适配文件，新增规则只加一个规则模块并接通路由，新增辅助脚本只加一个脚本文件，新增收编来源只给白名单加一行且同样受排除原则约束，新增资产类别使用下一个空闲编号，新增术语按术语表维护规则追加，新增记忆层按层表格式加一行，裁定结论只追加进 `900_ADR/` 的决策记录。

- 编号留空位供插入，顶层编号留空号位，资产带 210 到 250 之后从 260 起空闲，收件箱暂存族 010 之后从 020 起空闲，插入新项不得改动已有目录的编号。

- 新增规则、术语或类别时先写清适用范围、触发条件与落点，再写入。已定规则不得原地改写，变更时追加一条决定并显式声明被替代的旧条目。

## 参数与部署前确认

- 收集 ROOT，即收口目录的绝对路径，格式为父路径加 010_oc-ledger，根目录名固定，父路径随机器不同。

- 收集机器名，用于根 README 的路径映射表。

- 确认目标位置是否已有骨架，已有 AGENTS.md 与分区目录时只核对与补齐，不重建，不覆盖已有文件。

- 确认机器上是否已有知识库在别处，已有时不搬动它，知识库在收口目录内的正式位置是 050_Knowledge 下的 Obsidian 目录，搬入知识库需要单独指令。

- 确认是否存在大小写不同的同名目录，已存在时不擅自改名，先问人。

- 收集 git 身份，先查机器已有的全局身份，有就不用重设，没有就问人要，不编造。

- 收集要接入的 agent 工具清单，每个工具对应一份接入约定。

- 收集 skill 事实源仓库的地址与部署命令，问不到时走手动步骤兜底，不复制设备上已装的 skill 副本。

- 执行前设置 ROOT 变量，后续命令一律使用该变量。

## 执行部署

### 阶段 1 建目录

- 按 references/templates.md 中的目录树与编号规则建目录，050_Knowledge 下的 Obsidian 目录只建空目录，不搬入知识库。

- 部署产生的每个空目录放一个 `.gitkeep` 占位（含被根仓库忽略的运行时目录，其 `.gitkeep` 在 `.gitignore` 里开否定例外；敏感区 `210_Personal-record/` 除外，整体不进版本控制），使骨架可经 git 克隆完整复现，清单与口径见 references/templates.md「建目录」一节。

- 建完后用 find 列出结构并与目录树逐项核对。

### 阶段 2 写根文件

- 按 references/templates.md 写六个根文件，AGENTS.md 写最小内核，敏感区限制、删除确认与授权要求必须常驻，不得降级。

- CONTEXT.md 按 references/glossary.md 誊抄，标题写 CONTEXT.md，分组降为二级标题，导语中的本节改成本文件，节号指向本 skill 原文。

- 已存在的文件不覆盖，只补齐缺失的部分。

- 同时写 `.agents/rules/decision-records.md`、`.agents/rules/rule-design.md`、`.agents/rules/memory-system.md` 与 `.agents/rules/draft-review.md` 四份首批规则模块（模板见 references/templates.md），AGENTS.md 任务路由中的对应行随模板一起写入。

- 同时写 `.agents/scripts/extract.py` 抽取脚本（模板见 references/templates.md），供阶段 6 调用。

### 阶段 3 建根版本控制仓库

- 按 references/templates.md 建仓库，写入 gitignore、editorconfig 与 gitattributes，编码配置只作用于根仓库，不复制到子仓。

- 产物索引是忽略例外，提交前强制加入一次，之后作为已跟踪文件正常提交。

- 提交前检查 git status，确认被忽略的目录不在待提交列表里，例外只有两类：强制加入的产物索引，以及各空目录的 `.gitkeep` 占位（被忽略目录的 `.gitkeep` 经 `.gitignore` 否定例外放行，应出现在待提交列表里）。

- 用户明确不要根仓库时跳过本阶段，资产清单与产物索引暂行放在各项目目录内，不停下整个部署。

### 阶段 4 写接入约定

- 每个要接入的工具在 adapters 目录下写一份接入约定，含四条固定内容加一条本工具实际写法，写不出的先空着并标注待真实接入后确认，不编造。

### 阶段 5 部署 skill

- 先查 skill 事实源仓库是否有 bootstrap、curator、doctor 三个 skill：有则部署，部署命令与仓库地址记入对应适配文件；部署后做一次性比对，列出本机独有或版本不同的 skill 交人决定是否回收，比对不属于自检常驻校验。

- 事实源仓库无此三者（或问不到来源）时跳过本阶段：在对应适配文件中记录事实源仓库地址、查询日期、缺失名单，并注明以手动步骤兜底（日常规则的手动步骤即替代做法）；部署继续，不因此停下，不复制设备上已装的 skill 副本冒充部署。

### 阶段 6 收编已有资料

- 只在机器上已有 agent 工具产生过资料时执行本阶段，没有就跳过。

- 顺序不能倒，先收编，再接入。按 references/adopt.md 的白名单只读抽取，不移动原物，结果落到 imported 下的待判断区。

- 列出抽取清单交人判断归属，人工确认后才分流进正式分区，未经判断不得进入正式分区。

- 抽取副本不构成权威，agent 不读取它，沉淀并记录来源与抽取日期后即与源记忆脱钩，冲突时以工作区为准。

### 阶段 7 验收与收尾

- 按 references/acceptance.md 逐条验收，全绿才算完成。

- 验收通过后写当日流水，账本覆盖更新为当前任务无、队列空，并提交根仓库。

## 部署后的规则来源

- 收口目录投入使用后的日常规则在 references/operating-rules.md 中，包括闭环、产物归口、记忆与账本、保留与清理、代码规则、规则层级与禁止清单。

- 部署本 skill 的 agent 在后续会话中继续以本 skill 为规则来源，不另查文档。

- 规则冲突无法并存时停机报人，冲突项写入账本的堵塞段，人裁定后把结论按 ADR 方案记入部署好的工作区内的 `900_ADR/`，agent 读到更新才继续该项写入，裁定前该条保持停止，其余工作不受影响。

- 决策记录用 ADR：一条决定一个文件，存于部署好的工作区内的 `900_ADR/`，文件名从 0001 顺序编号，格式见 references/templates.md 的“决策记录（ADR）”一节。只追加，不修改已有条目；决定变更时写新 ADR 并标注旧的被取代。决策记录放在工作区内而不放在本 skill 里，这样本 skill 保持通用可复用，各次部署的裁定互不干扰。

- 知识库规则文件的自我定位修改必须等根规则文件到位后一并执行，上级文件不存在时不得提前修改，否则会制造悬空引用。
